# O4：PaperMate 的 RED、连接池上限与容量对照

## 结论

在本次华为云主机、单 Uvicorn worker、固定 1,000 条模拟论文、真实 PostgreSQL
的条件下，单连接池在约 340～353 目标请求/秒附近明显排队并出现超时；粗测中
353 请求/秒时成功吞吐为 335.1 请求/秒，错误率 6.25%，说明已越过可稳定服务的上限。
不能将这个过载吞吐直接作为可用容量。

本实验自定目标为成功率至少 99%、成功请求客户端 p99 不超过 200 ms。
单连接池最高已测达标目标点是 **325 请求/秒**（实际成功吞吐 327.4/s、零错误、
p99 173.84 ms）；340 请求/秒时 p99 316.72 ms，已不达标。
因此已测的达标边界落在 **325～340 目标请求/秒之间**，不是声称精确容量等于 325。

池扩为 4 后，最高已测达标目标点为 **458 请求/秒**（实际成功吞吐 457.0/s、
1/13711 请求失败、p99 144.14 ms、达标请求比例 99.61%）。599 请求/秒时不达标。
最高已测达标目标点比单连接池提高约 **41%**，没有随池大小变为四倍。
这是短阶段实验观察，不是长期容量承诺。

## 环境与控制变量

- 主机：Ubuntu 24.04，4 vCPU、约 7.4 GiB 内存，80 GiB ext4 云盘。
  系统显示 CPU 0/1 同属一个物理核、2/3 同属另一个物理核；两个物理核均为 SMT。
- 业务：根目录 `backend/`，`GET /api/papers/discover?page=1&page_size=20`。
  保留真实用户认证及两条论文 SQL；不调用大模型/arXiv，不人为添加 sleep 或 SQL 延迟。
- 数据：固定 1,000 条 `o4-synthetic-v1` 模拟论文；脚本重复运行不会重复插入。
- API：一个 worker，CPU affinity 2,3；连接池 max_overflow=0，获取超时 0.5s。
  PostgreSQL、Redis、Go 压测器及独立 Prometheus 使用 CPU 0,1（数据库与压测器共享资源）。
- R1 和临界点补测 pool_size=1；R2 pool_size=4；其余代码、数据、接口和绑核一致。
- 每阶段 30s，泊松开环到达。Go 压测器发送滞后 p99 约 1.05～1.07ms，正式阶段 CPU
  约 3%～9%，未出现 dropped、网络错误或 warn，压测机没有显示出瓶颈征兆。
- 代码基线 `5a06900577f677f3fcc863d363f9760355d0fa66`，本地分支 `lab2/o4`。
  测量时使用包含未提交改动的源码快照，不冒充该基线提交本身。实测源码已展开保存在
  `runs/o4/measured-source/`，原始归档 SHA-256：`4267e65dc91d0e101492aecf7335211a99add427849a8b449206f58f1a2de92e`。
  每次实验的 meta.json 还保存实际 Go 源码、二进制哈希及运行参数。

## 先预测、后测量

1. Go 低负载基线 `b2-go-pool1-01/server.json` 阶段 2：每请求连接持有 2.6927ms，
   每请求 API CPU 2.8360ms，每请求 checkout 为 1 次。
   初步计算池上限 1/0.0026927≈371.4/s，单 worker CPU 上限 1/0.0028360≈352.6/s。
   所以第一次预测为 CPU 略早达到上限，保存在 `PREDICTION-R1.json`，未事后修改。
2. R1 实测先出现单连接池排队：353 请求/秒阶段平均池占用 1.0，获取连接中的调用
   约 165.7 个，API CPU 仅约 0.767 核，而错误均为 503。之后扩大池明显改善同负载，
   支持单连接池是最先需要处理的瓶颈。
3. 不一致原因：每请求 CPU 随负载变化。247 请求/秒阶段 CPU 已降为 2.0872ms/request，
   比低负载降低约 26%；同时持有时间不含 checkout 之前已预留连接槽位的 pre-ping/
   建连时间，简单 P/H 是近似上限，不能精确预测尾延迟；高利用率下泊松突发会排队。
4. R2 前使用 R1 未过载的 247/s 阶段重新估计 CPU≈479.1/s、四连接池理想上限≈1705.7/s，
   预测池压力改善、下一个限制接近 CPU，而非吞吐变为四倍。预测在 `PREDICTION-R2.json`。
   补测的区间预测另存 `PREDICTION-R1-REFINE.json`，也在补测前写入。

## 指标实现与口径

- RED：`papermate_http_requests_total{method,route,code}`、
  `papermate_http_request_duration_seconds` 直方图、`papermate_http_inflight_requests`。
  route 使用完整模板，未知路由统一 `__unmatched__`；没有 UUID、查询参数或 Token 标签。
  /metrics、/health、/version、文档接口不计入 RED。
- 服务端延迟从监控中间件入口到最后一个响应体发送完成；异常提前发生则到异常。
  不包含进入中间件前的运行时/内核排队、网络传输和客户端发送滞后；也不计之后的后台任务。
- 连接池：`checked_out` 包含池内部已预留的槽位；`capacity` 是 pool_size+max_overflow；
  `acquiring` 为正在获取连接的调用数，包含排队、建连及 pre-ping，不能称为纯等待者数。
  `acquire_seconds{outcome}` 为实际 Pool.connect 调用耗时，不能称为纯排队时间。
  `hold_seconds` 为 checkout 到 checkin 的持有时间，包含认证/查询和事务生命周期；
  `timeouts_total` 为获取超时计数，接口层将其映射为 503。
- 服务端查询使用每阶段 [start+5s,end-1s] 窗口；客户端原始 CSV 是整个阶段。
  因采样、完成时刻与计划到达归属不同，计数和延迟可能略有差异，特别是过载阶段。
  server_error_rate 只统计 5xx，客户端包括非 2xx、超时和网络错误；server_rps 包含失败请求，
  不能用它冒充成功吞吐。过载时不能用包含廉价 503 的平均 CPU 推算成功请求容量。
- 服务端 p99 是直方图插值，尤其 0.5～1s 桶很宽。比如 R1 353/s 阶段服务端估计
  p99≈961ms，客户端成功 p99≈504ms，不能据此断言网络或服务端真慢了一倍。
  阶段窗口、样本总体不同及桶插值都会产生差异。本实验用客户端成功 p99 判断约定目标。
- 每秒采样的 checked_out 均值每阶段只有约 24 个样本，低占用时误差明显。
  不能把单 worker 的 CPU 上限当成整个 4-vCPU 主机或完整 PaperMate 系统的上限。

O4_TEST_PASSWORD 和私密 JWT_SECRET_KEY，执行 `uv sync --locked --all-groups`、
`uv run --locked alembic upgrade head` 和 `uv run --locked python scripts/seed_o4.py --count 1000`。

按记录的绑核/池参数启动，并启动独立 Prometheus。然后在 backend/ 中执行：

```bash
taskset -c 0,1 uv run --locked python scripts/o4_go_run.py \
  --name new-run-name --kind formal --rates 300,325,340 --step 30 --api-pid 实际API进程号
```

每次换新名字；读取测试密码和数据库地址的环境变量不要写入命令参数或提交。
仓库普通克隆由 Git 记录来源，云端快照由 SOURCE_MANIFEST.json 记录来源。单 worker
的 Python 指标没有配置多进程合并，不能直接改成多个 worker 后照用这些指标。
