## 新增流水线

CI 对 main 的 PR 与 push 运行，不做路径过滤。backend、frontend 检查通过后，
package job 构建 wheel 与静态文件，生成包和校验和并校验包内信息。
PR 构建只验证、不上传主干制品；main push 上传制品，保留 14 天。
环境固定 ubuntu-24.04、Python 3.12.10、Node 24.14.0、uv 0.11.28。
依赖分别使用 uv.lock 和 frontend/package-lock.json。

Release 工作流接受 vX.Y.Z 标签，先验证标签提交在 origin/main 历史中，
再运行检查、构建、打包和追溯，最后创建含 tar.gz 与 .sha256 的 Release。
相同发布版本不覆盖；更正使用新版本。release 不自动部署业务或迁移数据库。

## 与 Go 示例的差异

1. 单个 Go 项目改为 Python 后端和 JavaScript 前端，需要两套检查和工具链。
2. Go 二进制改为 wheel + 静态文件；解释器、第三方依赖和数据库不会打进包，
   运行安装清单从锁文件导出，安装时验证每个依赖的哈希。
3. Python 用 setuptools package-data 将 JSON 装入 wheel；/version 从包内读取，
   并与包根目录及前端的 BUILD_INFO 对照。整体发布版本独立于内部 wheel 的 0.1.0。
4. 业务依赖 PostgreSQL、Redis、Celery、arXiv 与模型服务。
   CI 中非 integration 测试使用既有替身，不声称覆盖完整外部系统；
   frontend 覆盖率也仅针对配置中指定的基础单元模块。
5. CI 与 Release 都重新构建，版本信息会改变制品；不声称完全可重复构建。
   归档时间等元数据未归一化，runner 镜像仍会更新。
6. 程序回退用原 Release 文件，数据库 schema 是否向后兼容需另行确认。
