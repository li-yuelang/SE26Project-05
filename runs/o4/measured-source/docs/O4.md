## Metrics contract

- `GET /metrics`: Prometheus text; no auth, bind the API to loopback.
- `papermate_http_requests_total{method,route,code}` counts completed middleware
  invocations. Unhandled errors before response headers use code 500.
- `papermate_http_request_duration_seconds{method,route,code}` is a histogram in
  seconds, from middleware entry until the final response body is sent. If the
  application raises first, it ends at that exception. It excludes later
  background work, TCP/network timing, and time before middleware entry.
- `papermate_http_inflight_requests` tracks all included in-flight HTTP requests.
- System endpoints `/metrics`, `/health`, `/version`, `/docs`, `/redoc`, and
  `/openapi.json` are excluded from HTTP RED metrics. Unknown routes share
  `__unmatched__`; route templates preserve `/api`. No IDs, query strings or
  tokens are labels.
- Use ONE uvicorn worker. These in-process metrics are not configured for
  multiprocess aggregation. Stream failure after response headers retains the
  actual HTTP status; RED alone does not measure asynchronous task completion.
- `deploy/o4/queries-red.txt` contains rate, 5xx fraction, p99 ms and mean ms.
  A zero-traffic error fraction is undefined. 401/403 are counted as separate
  statuses but excluded from the server 5xx error fraction.

## Seed the explicit test database

From `backend/`, set `DATABASE_URL` explicitly to the local O4 test PostgreSQL
instance, and set `O4_TEST_PASSWORD` to a private random value of at least 12
characters. Do not commit credentials or use the production database.

```bash
uv sync --locked --all-groups
uv run --locked alembic upgrade head
uv run --locked python scripts/seed_o4.py --count 1000
uv run --locked python scripts/seed_o4.py --count 1000
```

`DATABASE_URL` must have a loopback hostname; it is not implicitly taken from
`.env`. The script adds synthetic `o4-synthetic-000001` through `001000` papers
with stable UUIDs, dates and content, plus account `o4_bench@example.com`.
There are no external calls, deletes or updates to existing records/passwords.
The same password must be supplied on reruns. It prints synthetic and total
paper counts, never credentials. A smaller later count does not delete data.
Use a fresh dedicated DB for formal runs and record the printed total count.

Start the API with `uvicorn app.main:app --host 127.0.0.1 --port 18080 --workers 1`.
Log in once at `/api/auth/login`, then call
`GET /api/papers/discover?page=1&page_size=20` with its Bearer token. Registration
and login are setup traffic, not the measured workload. Never put the token in
a URL or saved load-test metadata.

## Connection pool measurements

`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, and `DB_POOL_TIMEOUT` configure the API pool
(defaults 200, 100, 30 seconds). O4 uses pool_size=1 or 4, max_overflow=0,
pool_timeout=0.5 seconds, one worker. Pool exhaustion becomes HTTP 503.
No artificial SQL delays or business-query changes are introduced.

- `papermate_db_pool_checked_out`: current borrowed connections.
- `papermate_db_pool_capacity`: pool_size + max_overflow, per worker.
- `papermate_db_pool_acquiring`: acquisition calls in progress, NOT pure waiters.
- `papermate_db_pool_acquire_seconds{outcome}`: actual Pool.connect duration;
  includes queueing, new connections, and pre-ping. outcome=success/timeout/error.
- `papermate_db_pool_hold_seconds`: checkout until checkin, including the whole
  transaction/application lifetime, not only SQL execution time.
- `papermate_db_pool_timeouts_total`: pool acquisition timeout count.

Pool capacity estimate = P / H, where H is total returned connection-hold
seconds divided by HTTP requests in the same steady window. Multiple checkouts
per request are included; checkouts_per_req is reported separately.
API CPU estimate = one Python worker CPU-second per second / CPU seconds per
request. This is approximate: low-load CPU cost changes with load, and allocated
vCPUs are SMT siblings. PostgreSQL shares generator cores, so generator lag and
CPU are checked, and host/container interference remains a limitation.

`scripts/o4_run.py` uses Poisson open-loop arrivals, records planned-to-response
client latency, and preserves requests.jsonl, steps.csv, server.csv, raw metrics,
raw Prometheus query responses, and vmstat/mpstat/iostat/pidstat logs. Token is
only kept in memory. Each 30-second stage excludes first 5 seconds and last 1
second for steady client/server comparisons. Server counters are scrape- and
completion-based; client records are assigned by planned arrival. Boundary
differences are expected, especially with a growing queue. Runs never overwrite.
The runner stops after generator lag p99>10ms, generator CPU>80% of one logical
CPU, any dropped arrivals, or fewer than half scheduled arrivals succeeding.
These are experimental validity/overload guards, not a service SLO.
